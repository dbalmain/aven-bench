# Results — harness A/B (`harness-01`)

Pre-registration: `analysis/prereg-harness-01.md` (committed before the first
attempt; Amendment 1 recorded from the runner's startup line, Amendment 2 from
operational health only, both before any outcome distribution was inspected).
Report generated by `analysis/harness-ab.ts` (committed `1211b35` before the
arms finished, effort-reporting defects fixed in `99e2c62`).

Runs: `phase6-harness-codex-01` (arm A), `phase6-harness-opencode-01` (arm B).
GPT-5.6 Luna both arms, reasoning effort `high` both arms and recorded per row,
71 holdout tasks × 2 samples, aven-lang `8ca8620`, doc v2 `dfa665f6`, rounds ≤
3, nudges 2, `no-verify`, hidden suite, bubblewrap, text diagnostics.

## Headline

**Arm B wins the primary DV.** Driving the same model through `opencode` rather
than `codex` reached a green suite on materially more tasks.

|                           | A: codex | B: opencode |
| ------------------------- | -------- | ----------- |
| rows written              | 141      | 155         |
| excluded `harness_error`  | 0        | 0           |
| excluded contaminated     | 5        | 0           |
| green rate (paired tasks) | 70.1%    | **82.8%**   |
| censored repair rounds    | 1.642    | 1.343       |
| first-shot                | 39.6%    | 43.3%       |
| output tokens per green   | 22,631   | **5,936**   |
| wall time                 | 7.4h     | 3.4h        |

Primary, as pre-registered — paired Wilcoxon on 67 per-task green rates:

```
diff (B − A)   +12.7 pp
Wilcoxon n (non-zero) 19   48 zero-diff pairs dropped
z 3.370   p 0.0008
```

**VERDICT: ARM B BETTER.** Above the pre-registered 10.0 pp bar.

### The secondary DV is significant and still does not clear its bar

Censored repair rounds came out −0.299 in arm B's favour at p = 0.0031 —
significant, and **0.001 rounds short of the pre-registered 0.3-round bar**, so
it is reported as below-bar rather than as a win. Reading a p-value that small
as support for the effect would be exactly the post-hoc move pre-registration
exists to prevent. The primary DV carries the result; this one is consistent
with it and decides nothing on its own.

`firstShotPass` is 39.6% vs 43.3%, p = 0.535 — no round-0 difference. The gap
opens during repair, not in the first attempt, which is where a tool loop would
be expected to matter.

## What the four dropped tasks do to the reading

67 of 71 tasks paired. All four drops were caused by **arm A**:

| task                     | why dropped                                   |
| ------------------------ | --------------------------------------------- |
| `leap`                   | Amendment 1 — smoke attempts satisfied resume |
| `prism`                  | 1 of 2 arm-A samples contaminated             |
| `split-second-stopwatch` | both arm-A samples contaminated               |
| `zipper`                 | both arm-A samples contaminated               |

Arm B held 2 usable samples on all three contamination-dropped tasks and scored
1 pass / 1 fail on each. Arm A scored 1 pass in 6 attempts across the same
three. **Including them would have widened the gap in arm B's favour**, so the
exclusion is conservative with respect to the winner and does not threaten the
result.

## Contamination is itself a finding, and it is one-sided

Five arm-A rows tripped the contamination gate; zero arm-B rows did.

| rules tripped                                                    | rows |
| ---------------------------------------------------------------- | ---- |
| `canonical-data`                                                 | 3    |
| `canonical-data`, `github-api-exercism`                          | 1    |
| `canonical-data`, `github-api-exercism`, `upstream-exercise-dir` | 1    |

One of these also recorded an `outsideWorkdirTouches` of 1. The codex arm went
looking for upstream Exercism test data on three tasks; the opencode arm never
did. Whether that is the harness's system prompt, its sandbox conventions or the
model's behaviour under that prompt is not separable here — it is a property of
the route, like everything else this round measures.

## Reliability runs the other way

The pre-registration requires pre-retry error rates to be reported alongside
post-retry ones, because cleaning them away would hide the most operationally
relevant difference measured.

| arm         | pre-retry harness errors | kind              | post-retry |
| ----------- | ------------------------ | ----------------- | ---------- |
| A: codex    | 0                        | —                 | 0          |
| B: opencode | 14 (9.0% of rows)        | `agent-no-tokens` | 0          |

Arm B is the arm that tripped its circuit breaker at 52/142 and needed the
threshold raised and a resume (Amendment 2). **So the arm that produced better
solutions was also the flakier route.** Both recovered fully under the single
pre-registered retry pass, so no capability claim rests on this, but a reader
choosing a harness should weigh both columns. Earlier opencode-go rounds ran
0.7% and 2.8% `agent-no-tokens`; whether 9.0% is a `gpt-5.6-luna`-on-gateway
effect or provider weather is not determinable from one round and is not
asserted either way.

## Efficiency

Arm A spent **3.8× the output tokens per green solution** (22,631 vs 5,936) and
2.2× the wall time. Arm A is subscription-billed and reports no cost at all; its
rows carry `costUsd: null`, never `0`, and **no cost DV was defined for this
round**. Arm B's measured spend was $0.85, comfortably inside the $2.47–$8.31
budget and well under the $6.00 halt rule.

Input tokens are reported per-arm and never differenced: the adapters disagree
about whether cache reads sit inside `promptTokens`, and summing across that
convention gap produced a spurious 44× gap before it was caught.

## Threats, restated against the result

1. **"Harness" here means the whole route, not the tool loop.**
   `opencode-go/gpt-5.6-luna` reaches the model through a gateway; codex goes
   direct to OpenAI. Same advertised model, different routing, possibly a
   different served version, system prompt or sampling default. This result
   supports "use this route for Aven", not "this tool loop is better".
2. **Concurrency is partial, not full** (Amendment 2). Arm B attempts 1–52 ran
   concurrently with arm A; 53–142 ran after the breaker tripped, still
   overlapping arm A's outstanding ~100 attempts but not from the same start.
   Still far closer than any model round, where arms were days apart — but the
   round's original "first fully concurrent comparison" claim is retired.
3. **The pinned compiler is stale.** `8ca8620` predates the `Bool`
   exhaustiveness fix and the bare-match-arm diagnostic. Correct as a control,
   but **the absolute rates here describe a compiler we no longer ship** and
   must not be quoted as current Aven capability.
4. **Effort pinning rests on a suggestive probe.** Both arms recorded
   `agentVariant: high`, so the arms were matched as claimed; that the flag is
   _live_ rests on a small reasoning-token probe. The arms did differ, so an
   unpinned-effort explanation is not the load-bearing one here.

## Conclusion

For running Aven benchmark work with GPT-5.6 Luna, **opencode is the better
route**: +12.7 pp green rate at p = 0.0008, on 27% of the output tokens and half
the wall time. The trade is reliability — 9.0% pre-retry gateway failures
against codex's zero — which the retry pass absorbs but which costs operator
attention and tripped a circuit breaker mid-run.

The direction was not predicted in advance and the campaign had no prior either
way, so this is a genuine two-sided result rather than a confirmed expectation.
